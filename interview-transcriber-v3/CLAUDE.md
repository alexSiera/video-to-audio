# CLAUDE.md

Постоянные правила для ассистента (Cursor / Claude Code / любой AI-агент), работающего с этим репозиторием.
Действуют на **всё** содержимое `interview-transcriber-v3/`. Эти правила не пересматриваются от задачи к задаче —
изменения только через явный апрув.

> Контекст проекта: SaaS-сервис транскрибации длинных интервью (до 10 ч), RU (primary) + EN.
> Архитектура: `docs/architecture/`. Roadmap: `TASKS.md`.

---

## 0. Жёсткие запреты (hard rules)

1. **Никогда не писать код без предварительного проектирования этапа.**
   Перед реализацией — объяснить архитектурное решение, предложить альтернативы, аргументировать выбор.
2. **Не использовать магические значения.** Все литералы, лимиты, TTL, веса и коэффициенты — через именованные константы или конфиг (env).
3. **Не дублировать код.** Общее — в `packages/`. Если один и тот же паттерн в трёх местах — вынести.
4. **Не коммитить секреты.** Никаких токенов, ключей, паролей в коде, тестах, примерах, комментариях. Секреты — только через env.
5. **Не ломать существующие тесты.** Любое изменение проверяется запуском тестов перед завершением.
6. **Не вводить циклические зависимости** между модулями/пакетами.
7. **Не создавать «god objects».** Один класс — одна ответственность.
8. **Не увеличивать сложность без необходимости** (KISS). Если решение можно сделать проще — делай проще.

## 1. Общие правила разработки

- Перед написанием кода:
  1. полностью спроектировать архитектуру (хотя бы для текущего этапа);
  2. объяснить выбранные решения;
  3. предложить альтернативы;
  4. аргументировать выбор;
  5. получить апрув.
- Каждый завершённый этап сопровождать документацией (обновлять соответствующий файл в `docs/`).
- После завершения задачи — отметить пункт в `TASKS.md`.
- Перед завершением этапа убедиться, что:
  - проект собирается (`make build` или эквивалент);
  - линтеры проходят (`make lint`);
  - тесты проходят (`make test`).

---

## 2. Архитектура

- **Clean Architecture** на бэкенде: `presentation → application → domain ← infrastructure`. Зависимости направлены внутрь.
- **Feature-first** на фронтенде: группировка по фичам, а не по типам файлов.
- Сервисы слабо связаны: API ↔ Worker — только через PostgreSQL и Redis-очередь (Dramatiq). Никаких прямых RPC.
- `apps/stt-service` — библиотека с интерфейсом `SpeechModel`, импортируется Worker'ом (не сетевой сервис в v1).
- Замена модели/движка (STT, диаризация, VAD) — через интерфейс, без правок остального кода.
- Подробности: `docs/architecture/system-design.md`.

---

## 3. Структура монорепозитория

```
apps/
  web/           Next.js + React + TS (frontend)
  api/           FastAPI (REST + WebSocket)
  worker/        Dramatiq workers (pipeline execution)
  stt-service/   SpeechModel interface + адаптеры (GPU)
packages/
  ui/            Переиспользуемые UI-компоненты (shadcn/ui-based)
  shared/        Общая логика (форматирование, константы)
  config/        Общие конфиги (eslint, tsconfig, prettier, ruff)
  types/         Общие TypeScript-типы (контракты API ↔ web)
docs/            Архитектура, research, runbooks
scripts/         Утилиты (bootstrap, dev-скрипты)
```

- Каждый сервис в `apps/` — независимый, со своим `Dockerfile`, `pyproject.toml`/`package.json`, тестами.
- Общие компоненты — в `packages/ui`.
- Общие типы — в `packages/types` (контракты REST/WS генерируются из OpenAPI, не пишутся вручную дважды).
- Общий код бэкенда (исключения, схемы, утилиты) — `packages/shared` Python-пакет, подключается как path-dep.

## 4. Ограничения кода

- **Один файл — желательно ≤ 300–500 строк.** Если больше — декомпозировать.
- **Одна функция — желательно ≤ 40–60 строк.** Если больше — выделить подзадачу.
- **Один класс — одна ответственность.**
- **Один модуль — одна тема.** Не смешивать несвязанное.
- Имена файлов: `kebab-case.py` для Python-модулей, `PascalCase.tsx` для React-компонентов, `camelCase.ts` для утилит.

---

## 5. Код-стайл

### TypeScript / React
- **TypeScript strict** режим (`strict: true`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`).
- Никакого `any` без обоснования в комментарии. Лучше `unknown` + type guard.
- Имена: понятные, без сокращений без необходимости (`user`, не `u`; `transcript`, не `tr`).
- Все публичные функции и компоненты — с JSDoc.
- React: функциональные компоненты, хуки. Никаких классовых компонентов.
- Импорты: абсолютные через `@/` (configured in tsconfig paths).

### Python
- **Python 3.12+**, обязательные аннотации типов на всех публичных функциях.
- `mypy --strict` (или `pyright`) на CI.
- `ruff` для lint+format (заменяет black + isort + flake8).
- Публичные функции — docstring (Google или reStructuredText, согласовано в `packages/config`).
- Имена: `snake_case` для функций/переменных, `PascalCase` для классов, `UPPER_SNAKE` для констант.
- Async для I/O (FastAPI, SQLAlchemy async); синхронный код только в CPU-bound воркерах/STT.

---

## 6. Тестирование

- Каждый новый модуль сопровождается тестами.
- **Unit Tests** — изолированно, с моками внешних зависимостей.
- **Integration Tests** — на реальных БД/Redis/MinIO (testcontainers или CI-сервисы), не на моках БД.
- Покрытие критичных путей (upload, pipeline, ACL) — обязательно. Цель: ≥ 70% на core-модулях.
- Запуск: `make test` (unit), `make test-integration` (integration).
- Имена тестов — описательные (`test_transcribe_rejects_corrupted_audio`, не `test_1`).

---

## 7. Git и коммиты

- Ветка `main` — стабильно собирается, тесты проходят.
- Фича-работа — в отдельных ветках `feat/...`, `fix/...`, `docs/...`.
- Коммит-сообщения — Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`, `ci:`).
- Один коммит — одно логическое изменение.
- PR/коммиты — только когда явно просят (правило harness).
- Перед merge в `main`: CI зелёный, ревью пройдено.

---

## 8. Зависимости

- **Не использовать устаревшие/заброшенные библиотеки.** Проверять активность мейнтейнера, дату последнего релиза.
- Lock-файлы обязательны: `uv.lock` (Python), `pnpm-lock.yaml` (Node).
- Запрет на пакеты с известными CVE — `pip-audit`, `npm audit`, `trivy` в CI.
- Новая зависимость ≥ средняя — обосновать в PR (зачем, альтернатив нет).

---

## 9. Документация

- Каждый публичный модуль — с документацией (docstring/JSDoc).
- После завершения этапа обновлять соответствующий документ в `docs/`.
- OpenAPI для API — автогенерируется FastAPI (`/docs`, `/openapi.json`).
- README каждого сервиса (`apps/*/README.md`) — краткое описание + как запустить локально.
- Контракты API ↔ Frontend — единственный источник правды: OpenAPI → генерация TS-типов в `packages/types`.

---

## 10. Производительность и масштаб

- Тяжёлые операции — только асинхронно (через очередь), никогда в HTTP-запросе API.
- GPU-память — один воркер = одна модель; последовательные этапы в рамках джоба.
- Большие файлы — через object storage + presigned URLs, не через БД и не через API-прокси.
- Пагинация — для всех списочных эндпоинтов.
- Кэш — Redis, с явными TTL, без «вечных» ключей.

---

## 11. Безопасность

- Все эндпоинты (кроме `/auth/*` и `/health`) требуют валидного access token.
- `user_id` берётся из токена, **никогда** из тела запроса.
- ACL на каждом ресурсе: серверная проверка владения перед любым действием/выдачей presigned URL.
- Валидация входов (Pydantic strict, allow-list enum, лимиты размера/длительности).
- Секреты — только через env. В образе их нет.
- Логи без PII: `user_id`, `job_id`, `trace_id`; без содержимого транскриптов, токенов, имён файлов целиком.
- Подробности: `docs/architecture/security.md`.

---

## 12. Наблюдаемость

- Структурированные JSON-логи (`structlog` / `pino`).
- Каждое действие в pipeline логируется с `job_id` и `trace_id` (OpenTelemetry).
- Ошибки — в Sentry (PII redaction включён).
- Метрики (post-v1): Prometheus.

## 14. Чего избегать

- Over-engineering: Kubernetes, service mesh, event sourcing, CQRS — **не в v1**.
- Micro-оптимизации до profiling.
- Кастомные велосипеды там, где есть зрелая библиотека (но — см. §8 про «не устаревшие»).
- Большие PR (≥ 800 строк) без предварительного обсуждения — разбивать.
- `print()` в Python, `console.log` в TS — только для отладки, не в коммите.
